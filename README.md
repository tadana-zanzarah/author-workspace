# Рабочее пространство автора

Веб-приложение для организации художественного проекта: серий/циклов, книг-проектов,
глав, сцен и рукописи, персонажей и их отношений, локаций с иерархией и историей.
Обычный режим работы — облачный: аккаунт и Supabase-backend, доступ с любого устройства
после входа. Приложение не требует build step и публикуется как статический сайт.

## Возможности

- аккаунт с email/паролем (Supabase Auth) и облачные контейнеры проектов;
- циклы (Series) и самостоятельные проекты, перемещение и сортировка проектов между циклами;
- главы, сцены (таймлайн, карточки, компактный список), теги, статусы написания и размещения;
- персонажи: анкета, участие в конкретных проектах, структурные связи (character links)
  и явные изменения эмоциональных отношений по сценам;
- локации: иерархия (родитель/потомки), канонический профиль с тематическими модулями,
  медиа-галерея, история локации (события);
- изображения персонажей и медиа локаций хранятся в Supabase Storage, база — только metadata;
- автосохранение, dirty-tracking редактируемых форм и защита от потери несохранённых данных;
- безопасная миграция локальных (legacy) данных в облако с preview перед записью;
- экспорт/импорт JSON и экспорт текста рукописи в локальном режиме.

## Локальный запуск

Требуется Node.js. Из корня репозитория запустите:

```powershell
node tools/server.mjs
```

Затем откройте `http://localhost:8000/`. Приложение использует ES-модули, поэтому запуск через
HTTP-сервер надёжнее прямого открытия `index.html`.

### LOCAL REVIEW

Одно действие, чтобы открыть в браузере текущую локальную версию (текущую ветку/HEAD рабочей
копии), без ручного запуска сервера и без запоминания localhost URL:

Вариант 1: VS Code → Terminal → Run Task → **Author Workspace: Open Local Review**

Вариант 2:

```powershell
npm run review
```

Открывается уже открытая (checked-out) локальная рабочая копия — push не требуется. Повторный
запуск переиспользует уже работающий сервер вместо того, чтобы падать с ошибкой занятого порта.
В правом нижнем углу появляется маленький служебный значок `LOCAL · ветка · commit` (только при
локальном запуске через `npm run review`/`node tools/server.mjs` — на GitHub Pages и в production
его нет).

## Проверки

```powershell
npm test
```

`npm test` запускает полный набор unit/data-safety тестов на Node (без браузера). Помимо этого
в `package.json` есть несколько десятков отдельных `npm run test:*` browser-тестов (Playwright +
локально установленный Microsoft Edge) — по одному сценарию/фиче каждый, например:

```powershell
npm run test:smoke
npm run test:dirty-browser
npm run test:accessibility-browser
```

Полный список смотрите в `scripts` внутри `package.json`.

## Аккаунт и облачные проекты

Обычный режим приложения — облачный: вход/регистрация через Supabase Auth, после входа
открывается список циклов (Series) и самостоятельных проектов. Проект можно создать, переместить
между циклами, отсортировать; цикл можно архивировать. Открытие проекта переводит приложение в
рабочее пространство (workspace) этого проекта.

Без заполненной Supabase-конфигурации (см. ниже) приложение остаётся в прежнем локальном
(legacy) режиме — это безопасный fallback для разработки и восстановления данных, но Auth и
«Мои проекты» в этом состоянии недоступны.

## Cloud-контент проекта

В облачном режиме следующее содержимое проекта хранится в Supabase и является authoritative
(источником истины), с записью только через транзакционные RPC с revision-контролем:

- главы, сцены (core-поля: заголовок, текст, дата/время, статусы, позиция, глава, локация),
  теги и scene tags;
- локации: канонический профиль, иерархия, тематические модули, медиа, события истории;
- персонажи: глобальная identity аккаунта, участие персонажа в конкретном проекте (роль,
  порядок, project-level overrides анкеты), структурные связи между персонажами, начальные и
  изменяемые по сценам эмоциональные отношения.

`localStorage` в облачном режиме используется только как last-good cache/recovery для этого
контента, а не как источник данных — он не является триггером записи в облако и не
подгружается в облако автоматически.

Отдельные local-only поля сцены (кто из персонажей что делает в конкретной сцене, на уровне
черновика взаимодействия) пока не синхронизируются и остаются только в локальном кэше проекта.

## Персонажи

Персонаж имеет глобальную identity, общую для аккаунта, и отдельное состояние участия в каждом
проекте (роль, порядок, project-level переопределения анкеты). Структурные связи персонажей
(родство и другие устойчивые связи) независимы от эмоциональных отношений по сценам. Фото
персонажа хранится в Supabase Storage; исходное изображение никогда не заменяется результатом
кадрирования — crop хранится отдельно как metadata.

## Локации

Локация имеет канонический профиль (название, официальное имя, алиасы, тип, краткое описание) и
иерархию родитель/потомки. Профиль раскрывается адаптивными тематическими модулями (география,
атмосфера, население и культура, управление и экономика и др.) — состав модулей можно выбирать
на уровне участия локации в проекте. У локации есть медиа-галерея (изображения в Supabase Storage)
и история — хронологические события с датой, описанием и порядком.

## Локальный (legacy) режим и `?local=1`

Явный query parameter `?local=1` — безопасный локальный recovery/legacy-режим: он открывает
прежнее локальное рабочее пространство в обход облачного входа и используется частью старых
editor regression tests. При заполненной Supabase-конфигурации обычный вход на `http://localhost:8000/`
и на GitHub Pages не требует никакого query parameter — облачный Auth является режимом по
умолчанию.

Каждый открытый облачный проект использует собственный локальный ключ
`authorWorkspace:project:<cloud-project-uuid>`. Исторический ключ `novelTimelineV11` (старое
локальное рабочее пространство до появления аккаунтов) сохраняется без автоматического переноса
или удаления.

## Миграция локальных данных в облако

Для пользователей с данными в старом локальном рабочем пространстве есть мастер миграции: любое
преобразование начинается с preview без побочных эффектов, конфликтующие/неоднозначные ссылки и
сопоставления персонажей требуют явного решения пользователя, а исходные локальные данные никогда
не удаляются автоматически после успешного переноса. Прямой импорт произвольного local JSON поверх
уже существующего облачного проекта не поддерживается — только через мастер миграции.

## Импорт/экспорт

В локальном (legacy) режиме доступны полный экспорт и импорт проекта в JSON (кнопки в интерфейсе),
а также экспорт текста рукописи. Из облачного рабочего пространства доступна выгрузка резервной
копии старого локального workspace (JSON) — например, перед его миграцией в облако.

## Структура

- `index.html` — production entry point;
- `css/` — стили интерфейса;
- `js/` — модули приложения: локальный режим (`app.js`), облачный режим (`cloud-app.js`),
  Supabase API-адаптеры (`cloud-*.js`), доменная логика (сцены, персонажи, локации, миграции,
  хранение, UI);
- `supabase/migrations/` — история миграций схемы Supabase;
- `supabase/tests/` — SQL-проверки (в т.ч. RLS) для локальной Supabase database;
- `supabase/scripts/` — read-only и migration-tooling для production Supabase (см.
  [docs/supabase-workflow.md](docs/supabase-workflow.md));
- `tools/` — локальный сервер, local review launcher и автоматические тесты;
- `reference/` — read-only исторические эталоны;
- `backup/` — неприкосновенные внешние резервные копии.

Build step для текущей версии не нужен: корень репозитория можно публиковать как обычный
статический сайт.

## Supabase

Supabase — облачный backend приложения: Auth (email/пароль), Postgres-схема аккаунта, циклов,
проектов и всего перечисленного выше контента проекта, RLS-политики и транзакционные RPC для
записи, а также Storage для изображений персонажей и медиа локаций. Подробная модель данных,
инварианты и concurrency-контракты описаны в [CLOUD_ARCHITECTURE.md](CLOUD_ARCHITECTURE.md) и
[AGENTS.md](AGENTS.md).

### Browser configuration без build step

Заполните только два browser-public значения в `js/supabase-config.js`:

```js
export const SUPABASE_CONFIG=Object.freeze({
  url:"https://YOUR_PROJECT_REF.supabase.co",
  publishableKey:"YOUR_PUBLISHABLE_KEY"
});
```

Publishable key (или старый `anon` key) разрешено использовать в публичном browser-коде:
безопасность строк обеспечивает RLS, а не сокрытие ключа. Никогда не помещайте в этот файл
`service_role` / secret key, database password, personal access token или private key.

Без конфигурации приложение продолжает открывать прежний локальный workspace (см. «Локальный
(legacy) режим» выше).

Для email Auth добавьте разрешённые redirect URL:

- local: `http://localhost:8000/`
- GitHub Pages: `https://tadana-zanzarah.github.io/author-workspace/`

Стандартная persistence Supabase Auth хранит session; приложение никогда не сохраняет пароль
самостоятельно.

### Применение миграций

Миграции лежат в `supabase/migrations/`. Для локальной проверки примените их к локальной Supabase
database и запустите SQL-тесты из `supabase/tests/` (каждый работает в транзакции и завершается
`rollback`). Любое взаимодействие с production Supabase database — только через инструментарий из
[docs/supabase-workflow.md](docs/supabase-workflow.md); ручной Supabase SQL Editor и произвольные
connection strings для production не используются.
